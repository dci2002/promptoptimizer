## Decision

- [2026-09-22 14:20:00] HL (Human-in-the-loop) is implemented via an in-memory `threading.Event` bridge (`HLBridge`) injected into `ReActAgent`, NOT the template's `srcprompt.txt`/`dstprompt.txt` file polling. `srcprompt.txt` is still written (for audit), but the wait is event-based and the user responds through the GUI "Result prompt" field + "Continue" button.

- [2026-09-22 14:20:00] All dialogs (LLM add/edit, variable add) are in-page modals in the single pywebview window — no separate pywebview windows (simpler state, no cross-window IPC).
- [2026-09-22 14:20:00] Long-running optimization executes on a dedicated worker thread; JS polls `api.get_state()` every 500 ms (pywebview GUI-thread constraint: Api methods must return fast).
- [2026-09-22 14:20:00] `scripts/template/` is treated as an immutable reference: code is adapted/copy-modified into `scripts/core/`, never imported.
- [2026-09-22 14:20:00] `core/` has zero pywebview dependencies (unit-testable headless); `ui/api.py` is the only bridge; UI never calls langchain directly.
- [2026-09-22 14:20:00] Per-run files are isolated in `workspace/` (fresh per Start), not the app root as in the template's CLI layout.
- [2026-09-22 14:20:00] Agent logging: template `print()` calls replaced with an `on_event(str)` callback forwarded to the "Progress" field (bounded deque, 500 lines).
- [2026-09-22 14:20:00] Role mapping: "LLM as Judge" = llm2 (target executor tool) in the optimization loop; "LLM for prompts" = llm1 (ReAct agent). "Run prompt" executes the prompt on LLM as Judge per req 3.5.

GUI backend: pywebview + PyQt6 (+ PyQt6-WebEngine, qtpy). GTK (`gi`) is NOT available in this environment; pywebview logs a harmless "GTK cannot be loaded" notice and falls back to Qt.

Known pywebview/Qt quirks worked around: `webview.destroy()` from a non-GUI thread hangs the loop (probe uses `window.hide()` + `os._exit()`); `evaluate_js` must receive a synchronous expression (async IIFEs serialize to `{}`); JS bridge probes must retry until `window.pywebview.api` is injected.

- [2026-09-22 20:13:00] save_llm bridge protocol: the `save_llm(cfg)` method accepts an optional `_old_name` field. If `_old_name` is present and matches an existing LLM, the method calls `update_llm(old_name, cfg)` (edit mode, including rename with role cascade). If `_old_name` is absent, it calls `add_llm(cfg)` (add mode, with duplicate-name rejection). The JS dialog sends `_old_name` only in edit mode. This single-method design avoids a separate `update_llm` bridge method and keeps the UI logic simple (one Save button for both add and edit).
- [2026-09-22 20:13:00] probe_ui.py Phase 2 verification: the headless probe drives the Settings tab UI end-to-end via synchronous `evaluate_js` calls (one DOM action per call, Python sleeps between steps). This avoids the pywebview quirk where async IIFEs serialize to `{}` and hang the probe. The probe runs against a **copy** of config.yaml in a temp dir (`tempfile.mkdtemp`), so the real project config is never mutated. Scenarios 3.1–3.4 are verified: Add (dialog → fill → Save → row appears + persisted), Edit (dblclick → prefill → change temp → Save → row + file updated), Remove (select → confirm stubbed → row gone + persisted), HL toggle (checkbox → change event → persisted as true). A global `signal.alarm(90)` timeout prevents indefinite hangs.
- [2026-09-23 12:22:00] `validate_run_inputs` is a pure function in `core/prompt_io.py` (not in `runner.py` as originally sketched in tasklist T3.2): it takes `(config_data, template, variables)` and returns a `list[str]` of error messages. The `Api.run_validation` bridge method normalizes the JS variables array (`[{name, value}]`) to a Python dict and delegates to this function. This keeps the validation logic headless-testable and decoupled from the runner (which doesn't exist until Phase 5).
- [2026-09-23 12:22:00] Variable names in the UI are validated client-side with regex `^\w+$` (letters, digits, underscore) to match the `extract_variables_from_prompt` regex `\{\{(\w+)\}\}` — preventing names that the extraction regex would not match (e.g., names with hyphens or spaces). Duplicate names are rejected client-side before the row is added.
- [2026-09-23 12:22:00] The validation strip re-runs on a 400 ms debounce after any change to prompt, result, variables, or roles (triggered by `scheduleValidation()`). The strip shows all errors joined by `·`; it is hidden when valid. This matches req 3.6 "on any change … re-run validation" without flooding the bridge with calls on every keystroke.
- [2026-09-23 13:39:00] Context menu Paste uses a Python bridge method `get_clipboard()` (QApplication.clipboard().text()) instead of `navigator.clipboard.readText()` or `document.execCommand("paste")`. Root cause: `navigator.clipboard.readText()` crashes the Qt backend (setFeaturePermission TypeError); `document.execCommand("paste")` does NOT fire a native `paste` event in Qt WebEngine. The bridge method reads the system clipboard directly via PyQt, returns the text to JS, which inserts it at the cursor position. Copy/Cut continue to use `document.execCommand("copy"/"cut")` which work fine in Qt WebEngine.
- [2026-09-23 18:52:00] "Load from workspace files" (`load_run_data`): the `Api` class now accepts a `base_dir` parameter (the workspace directory) in its constructor, passed explicitly from `main/app.py` as `os.path.join(PROJECT_ROOT, "workspace")`. The `load_run_data()` bridge method reads prompt.txt (required — raises FileNotFoundError if absent), result.txt (optional — empty string if absent), and for each {{var}} extracted from the prompt reads {var}.txt (optional — empty string if absent). Variable values are NOT stripped (multiline preserved), unlike result which is stripped. This matches the write side (write_run_files writes raw values).
- [2026-09-23 19:38:00] `core/llm.py` LLM layer (Phase 4): `LLM2Executor` is ported from the template with two deliberate deviations — (1) API-key validation is extracted into a shared `_check_api_key` helper (rejects empty and "your-api-key-here" placeholder) called from both `LLM2Executor.execute()` and `make_llm1()`, so a misconfigured key fails fast with a clear ValueError instead of a cryptic OpenAI 401; (2) langchain imports are lazy (inside `execute()`/`make_llm1()` call bodies) so the module can be imported and unit-tested without langchain installed. `reasoning_effort=None` is passed on every `ChatOpenAI` instantiation (T4.1+T4.2 rule). `make_llm1` defaults to temperature 0.1 and accepts an optional `verbose` kwarg for Phase 6 agent use.

- [2026-09-24 13:15:00] Phase 5 agent + dry-run architecture: `core/agent.py` ReActAgent uses lazy langchain imports (inside `_get_llm`, `_make_tools`, `run()`) so the module imports without langchain installed. `build_final_prompt` returns the **substituted prompt string** (not a file path) — it writes final_prompt.txt as a side effect. `agent.invoke({"messages": [...]}, config={"recursion_limit": N})` passes config as a **kwarg named `config`** (not positional). `run_optimization` in `core/runner.py` does a lazy `from core.agent import ReActAgent` — tests must patch `core.agent.ReActAgent`, not `runner.ReActAgent`. The Phase 5 `start_run` is a dry-run stub: it validates input (req 3.6) then spawns a daemon worker emitting 5 canned [DRY-RUN] progress lines with 0.5s sleeps — no real agent is launched (that's Phase 6). The GUI probe reads the authoritative `_running` flag by calling `api.get_state()` directly from the probe thread (not via `evaluate_js`, which cannot return Promises and whose DOM `btn.disabled` lags by up to 500ms due to the JS poll cycle).
- [2026-09-24 14:29:00] Phase 6 real start_run: `ui/api.py` start_run validates via `validate_run_inputs` BEFORE launching the worker thread (so validation errors return synchronously to JS with no worker spawn). The double-start guard checks `self._running` under `self._lock` and returns `{"ok": False, "error": "A run is already in progress"}`. The worker is a daemon `threading.Thread` that calls `run_optimization(self._config.data, template, result, var_map, self._base_dir, bool(hl), on_event=_emit)` with all arguments POSITIONAL (matching the function signature). `OptimizationResult` is imported from `core.runner` in `ui/api.py` (previously missing — only used in an annotation). The `_emit` callback appends to `self._progress` (a `collections.deque(maxlen=500)`) under `self._lock`. On success the worker sets `self._running = False` and `self._optimization_result = res.final_template`; on `ValidationAbort` or generic `Exception` it sets `self._running = False` and `self._optimization_result = ""`. Tests patch `"ui.api.run_optimization"` (where the name is looked up), not `"core.runner.run_optimization"`. The probe restores the judge LLM's original api_base after the Phase 4 break-judge error-path test (`_orig_judge` captured before the break) so the Phase 6 real run can reach a live server.
- [2026-09-24 19:54:00] Cooperative Stop for in-flight runs (user request): a shared `threading.Event` (`Api._stop_event`) is passed down through `run_optimization` → `ReActAgent` as a `stop_event` kwarg. The agent checks it at two granularities: (a) between LLM iterations in `run()` (via `_check_stop()` raising `StopRequested`) and (b) inside long tools (`llm2`, `analyze_prompt`) before each blocking LLM call so a stop request is honored quickly without waiting for a whole tool to finish. `StopRequested` propagates up to `run_optimization`, which returns `OptimizationResult(success=False, ...)` with a "stopped by user" marker instead of raising — the worker then clears `_running` normally. `Api.stop_run()` sets the event and appends a "[STOP]" progress line; `Api.shutdown()` (wired to `window.events.closed` in `main/app.py`) does the same, so closing the window during a run also aborts the worker cleanly. `get_state()` gains a `stop_button: {enabled: bool}` field — enabled while running. Test fakes for `run_optimization` in `test_start_run.py` / `test_hl_bridge.py` must accept the new `stop_event` kwarg (mock.patch side_effect functions receive every kwarg the worker passes).

The final prompt alone is sent as a single user message; `reasoning_effort=None` is still passed. Tests in `test_llm.py` updated to assert the messages list has exactly one user message.
## Rationale

- [2026-09-22 14:20:00] File polling blocks a thread for unbounded time and provides no UI feedback; an event bridge integrates cleanly with the GUI and keeps the tool contract (response format `ШАБЛОН:` / `ИЗМЕНЕНИЯ:`) identical to the template.
- [2026-09-22 14:20:00] Normalized LLM list supports the required Add/Edit/Remove table and role dropdowns; two hardcoded LLM slots cannot satisfy scenarios 3.1–3.4.
- [2026-09-22 14:20:00] In-page modals keep a single source of truth (one window, one Api) and avoid pywebview multi-window lifecycle complexity.
- [2026-09-22 14:20:00] Polling `get_state()` is the simplest robust pattern for pywebview (no websockets); 500 ms is responsive enough for log streaming.
- [2026-09-22 14:20:00] Copy-modifying (not importing) the template isolates the app from template layout assumptions (base_dir = script dir) and lets the workspace/ separation and logging hooks be introduced cleanly.
- [2026-09-22 14:20:00] UI/core separation enables headless unit tests of the entire optimization pipeline without a display.
- [2026-09-22 14:20:00] The template's CLI design writes prompt.txt etc. next to the script; for a GUI app a dedicated workspace/ prevents collisions between concurrent/sequential runs.
